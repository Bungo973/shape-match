# 文档交接审查（2026-09-27）

## 结论

当前文档足以启动**桌面端三战战斗原型**，并能统一多数核心规则：8×8、任意相邻不同方块交换、每回合 3 AP、主动基数 × 被动倍率、四类无属性炸弹、固定九战路线、非战斗嵌片安装、神器多来源与 Boss 向上重力。它还不能直接当作**完整九战首版的冻结规格**。下列机制与内容仍是候选或未定义；执行者不应把自己的临时选择写成已确定设计。

本文件只记录交接状态，不替代规则文档。数值如伤害、金币、价格、倍率阈值和局长已有占位值，可集中配置后试玩调整；以下缺口主要是**规则、内容与状态流程**，不能仅靠调数值解决。

## 文档权威顺序

1. [PRD](PRD.md) 确定产品范围与验收目标，[GAME_RULES](../GAME_RULES.md) 确定结算顺序，[SPECIAL_TILES](../SPECIAL_TILES.md) 确定炸弹行为，[MAP](MAP.md) 确定路线与战后流程。
2. [GRAVITY_DESIGN](../GRAVITY_DESIGN.md)、[BOARD_INSERT_VISUAL](BOARD_INSERT_VISUAL.md) 分别细化重力与棋盘嵌片显示；设计提案中的“候选／暂定／待讨论”不是正式内容池。
3. [MAP_IDEAS](MAP_IDEAS.md) 明确已停用；[NEXT_DESIGN_PROPOSALS](NEXT_DESIGN_PROPOSALS.md) 仅作灵感，不作为当前实现依据。发现规则冲突时记录并回到上述主文档统一，不从旧提案补规则。

## 可以直接交给执行者的工作

- 按 [PLAN 阶段 1](PLAN.md#阶段-1无美术战斗原型)建立纯状态结算引擎和桌面灰盒；使用固定种子、事件日志和现有候选图做一战视觉验证。
- 实现已定的相邻交换、未匹配保留、炸弹点燃与组合、主动／被动边界、AP、生命与护盾、毒气眩晕与回合末衰减、向上重力的状态框架。对上表 P0 情形先写固定棋盘样例并等待规格确认，避免把临时算法埋进核心引擎。
- 战后流程、嵌片几何、库存、旋转、合法落位、原位扩张、存档与 UI 层级可以先做。嵌片的效果注册和神器被动触发宜采用数据化接口，暂用明确标记的原型占位内容。
- 桌面端优先。手机宽度适配在桌面版验证之后；战斗中仍不得给走法建议或行动结果预览。嵌片覆盖层由代码绘制，现有石纹图不是嵌片素材。
